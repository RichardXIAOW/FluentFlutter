从 flutter create 到能接 PR 的工程骨架

这不是一篇"介绍"，是一份照着打勾就能做完的清单。每一步都写了：做什么 → 命令 → 产出文件 → 怎么验证自己真的做对了。

三条使用约定 ① 从上往下做，不要跳。顺序是有依赖的：先立门禁再写代码，后面所有代码自然合规；反过来要返工。
② 每一步的"怎么验证"必须真的跑一遍。没验证就往下走，问题会在三步之后以完全无关的样子爆出来，那时候排查成本是现在的十倍。
③ 左上角把项目名 / 包名改成你的，全站代码块会自动替换——命令可以直接复制粘贴。
关于"能不能跳步""从上往下"说的是依赖顺序，不是"每一步都得现在做完"。判断标准只有一条：后面哪一步会用到它？
· 真正的前置——阶段 1（没有工程什么都做不了）、阶段 2（门禁不先立，后面所有代码都要返工）、阶段 3.2（三条铁律决定了后面文件往哪放）。
· 可以延后——阶段 4 只做 AppSpacing，AppDuration 等到真有动画再加；阶段 9 可以先只建集中文案文件（9.1），接 arb（9.2/9.3）留到真要第二门语言时；阶段 10 的测试从阶段 6 结束就能建（那时已经有 Failure 可以测了），不必等到阶段 10。
· 建议尽早做——阶段 10 的"能写纯 Dart 测试的就别写 Widget 测试"这条习惯，越早养成越省时间。它不需要等任何前置。

阶段 0定名字与基线

编程最大的浪费是返工。flutter create 之前有三样东西必须定死，因为其中一样上架后永远改不了。

名字形态能不能改
项目名 project name小写+下划线，my_app改起来麻烦（要动 import 前缀）
组织包名 org反域名，com.example上架后不可改
应用显示名中文/英文随意，我的应用随时可改
红线Android 的 applicationId / iOS 的 bundle identifier 上架后不能改——改了就是一个新 App，用户要重新下载。所以 org 想清楚：别用 com.example，用你自己的域名倒写。
常见坑显示名不要和项目名混为一谈。项目名是给代码用的（my_app），显示名是给用户看的（"我的应用"），中间隔着一层平台配置。
怎么验证把三个名字写成一句话贴在 README 顶部：org=___ / project=___ / 显示名=___。然后做一次反向检查：搜一下你打算用的 org，确认对应的域名/IP 不是别人的——com.example 是官方保留的示例前缀，上架前必须换掉，用别人的反域名会构成商标风险。
bash
flutter --version
flutter doctor -v

flutter doctor 里每一项红色都要先解决掉，不要带着红叉往下走。尤其是 Android toolchain 和 CocoaPods，它们会以"某个插件编译不过"的形式在后面找上你。

怎么验证flutter doctor -v 没有红叉（✗）。黄叉（!）可以视情况保留，但要知道它是什么。
为什么这一步现在做把 Flutter 3.x.x / Dart 3.x.x 写进 README，就是一份团队契约。半年后新人报"我这跑不起来"，第一件事是对版本，而不是猜代码。
半年后你自己要升级时，按 附录 G · 升级检查单 的顺序做——别凭感觉升。
阶段 0 完成标志你手上有一句话：org=___ / project=___ / 显示名=___，而且 flutter doctor 干净。

阶段 1建工程

bash
# 在你想放项目的空目录里执行；. 表示"就建在当前目录"
flutter create --org com.example --project-name my_app --platforms=android,ios .

# 后面想补平台随时可以（原有代码不受影响）
flutter create --platforms=web,macos .
常见坑目录名和 --project-name 不一致时会报 "xxx" is not a valid Dart package name。项目名只能是小写字母、数字、下划线，不能有连字符和大写。
怎么验证cat pubspec.yaml 的 name: 是你想要的项目名；android/app/build.gradle（或 .kts）里的 applicationId 是 org + "." + project 拼出来的，例如 com.example.my_app。这两个值现在对了，阶段 12 的签名和上架才不会返工。
bash
cd my_app
flutter pub get
flutter run

跑起来以后，在终端里按：

  • r 热重载——只重跑 build，状态保留。改 UI 用这个。
  • R 热重启——重建整棵树，状态清空。改初始化逻辑、改 Provider 用这个。
  • q 退出。

注意原生代码（Android/iOS/插件的 Java·Kotlin·Swift 部分）热重载无效，必须完整重新 flutter run。
怎么验证改一行 Text 的字，按 r —— 界面立刻变，并且你刚才在页面上的操作状态（滚动位置、输入内容）都还在；再改一行初始化的代码（比如换掉 home:），按 R —— 状态清空。两个手感都对，说明你分清了。

阶段 2立规矩：静态门禁

这是整份清单里最容易被跳过、但最不该跳过的一步。理由只有一句：能由机器拦住的规范才叫规范；靠人眼和 Code Review 的规范，三个月后一定烂。

bash
flutter pub add dev:very_good_analysis
flutter pub add dev:import_lint
别手抄版本号让 pub add 自己取当前最新兼容版。你抄的版本号可能和你的 Flutter 版本对不上，而版本冲突的报错非常难读。import_lint 要求 Dart ≥ 3.10 / Flutter ≥ 3.38。
怎么验证cat pubspec.yaml 确认两个包都在 dev_dependencies: 下（不是 dependencies:）；flutter pub get 无 "version solving failed"；flutter pub deps --style=compact | head -5 能正常输出依赖树。装完不做这一步，就到阶段 2.3 才发现规则没生效，白排一遍。

删掉原有内容，整份替换成：

analysis_options.yamlyaml

analyzer:
  exclude:
    - "**/*.g.dart"
    - "**/*.freezed.dart"
  errors:

    invalid_annotation_target: ignore

# ── 架构边界：新 analyzer 插件机制（Dart 3.10+）──
# ★ 必须写在 analysis_options.yaml 里。
#   写进别的文件名（比如 import_lint.yaml）分析器根本不会读，规则静默失效。
plugins:
  import_lint: ^2.0.0

import_lint:
  rules:
    # ① presentation 不许 import data —— 页面只能通过 domain 接口拿数据

      target: "package:my_app/features/**/presentation/**"
      from: "package:my_app/features/**/data/**"
      except: []

    # ② core 是地基，不许反向依赖业务
    core_not_depend_on_feature:
      target: "package:my_app/core/**"
      from: "package:my_app/features/**"
      except: []

    # ③ domain 必须零 Flutter 依赖 —— 这样才能纯 Dart 单测
    domain_no_flutter:
      target: "package:my_app/features/**/domain/**"
      from: "package:flutter/**"
      except: []
最常见的失败点把 plugins: 和 import_lint: 两段写进了自建的 import_lint.yaml。分析器只读根目录的 analysis_options.yaml，所以那样写规则一条都不会生效——而且不会报错，你会以为自己在被保护，其实没有。
怎么验证改完存盘，重启分析服务器（VS Code：命令面板 → Dart: Restart Analysis Server；Android Studio：File → Invalidate Caches 或重启 IDE）。改 plugins: 段之后不重启是不生效的。

这一步不能省。规则最常见的失败方式不是"写错"，而是"看起来写对了但根本没加载"。

阶段 3骨架目录（目标形态）

先立一条规矩：现在不要 mkdir -p 建十几层空目录。空目录里没有代码，你就不知道每一层是为了什么而存在的；三个星期后你自己都忘了 services/ 和 providers/ 的区别。下面的树是目标形态，不是"现在就去建"——写文件时让 IDE 自动建父目录，目录跟着需求长出来，每一层诞生时你都知道原因。

# 其余目录：写文件时让 IDE 建。不要现在建空目录。
怎么验证ls -R lib 应该只有 lib/main.dart＋空的 app/、core/。一旦你发现自己在手动 mkdir 第三个目录，就把手停下——那说明你在建"以后可能用到"的目录，而不是"现在需要"的目录。
  1. domain 零依赖——不许 import flutter/、不许 import data/。它只放实体和"我要什么数据"的接口。好处：纯 Dart，测试 3 毫秒跑完，不需要起引擎。

  3. core 不许 import features——地基不能反过来依赖楼房。好处：core 可以被任何 feature 安全复用，不会形成环。

阶段 4设计令牌与主题

先有令牌，再有页面。反过来做的话，你会写 200 个裸数字再去全局搜索替换。

lib/core/theme/app_tokens.dartdart
import 'package:flutter/material.dart';

/// 间距令牌。全项目的间距只能从这里取，不许写裸数字。
abstract final class AppSpacing {
  static const double xs = 4;
  static const double sm = 8;
  static const double md = 12;
  static const double lg = 16;
  static const double xl = 24;
  static const double xxl = 32;
}

/// 圆角令牌。
abstract final class AppRadius {
  static const double sm = 6;
  static const double md = 10;
  static const double lg = 14;
  static const double pill = 999;
}

/// 尺寸令牌：按钮高度、缩略图这类固定尺寸。
abstract final class AppSize {
  static const double buttonHeight = 48; // 触摸目标下限，别再小
  static const double listThumb = 56;
  static const double appBar = 56;
}

/// 动画时长令牌。全项目动画时长统一，交互手感才会一致。
abstract final class AppDuration {
  static const Duration fast = Duration(milliseconds: 150);
  static const Duration normal = Duration(milliseconds: 250);
  static const Duration slow = Duration(milliseconds: 400);
}
为什么用 abstract final class它只放 static const，不需要被实例化，也不该被继承。abstract 挡住 new，final 挡住继承——这是 Dart 3 里"纯常量容器"的标准写法（比 class + 私有构造器干净）。详见 附录 E.2。
常见坑别用 enum 干这事。枚举值必须是实例，装不下 static const double。

令牌立好，紧接着就把它们焊进主题——不然每个页面还会各写一遍样式：

lib/core/theme/app_theme.dartdart
import 'package:flutter/material.dart';

import 'app_tokens.dart';

/// 品牌种子色。改这一个值，全站主色跟着变。
/// 品牌色允许硬编码（它不随深浅色模式变），语义色则一律从 ColorScheme 取。
const Color kSeedColor = Color(0xFF6750A4);

ThemeData buildLightTheme() => _base(
      ColorScheme.fromSeed(seedColor: kSeedColor, brightness: Brightness.light),
    );

ThemeData buildDarkTheme() => _base(
      ColorScheme.fromSeed(seedColor: kSeedColor, brightness: Brightness.dark),
    );

/// 圆角、按钮高度这类"全站一致"的东西，在这里统一兜住，
/// 免得每个页面各写一遍 style。
ThemeData _base(ColorScheme scheme) => ThemeData(
      useMaterial3: true,
      colorScheme: scheme,
      scaffoldBackgroundColor: scheme.surface,
      filledButtonTheme: FilledButtonThemeData(
        style: FilledButton.styleFrom(
          minimumSize: const Size.fromHeight(AppSize.buttonHeight),
          shape: RoundedRectangleBorder(
            borderRadius: BorderRadius.circular(AppRadius.md),
          ),
        ),
      ),
      inputDecorationTheme: InputDecorationTheme(
        border: OutlineInputBorder(
          borderRadius: BorderRadius.circular(AppRadius.md),
        ),
      ),
    );
深色模式翻车三件套① 硬编码 Colors.white/Colors.black；② 文字颜色写死而不从 scheme.onSurface 取；③ 图片上盖了写死的白底。规则：除了品牌色，一切颜色都从 ColorScheme 取。
怎么验证flutter analyze 干净；再写三行 test 断言 AppSpacing.md == 12、buildLightTheme().colorScheme.brightness == Brightness.light、buildDarkTheme() 不为 null。令牌是"全项目唯一的数字真相"，它错了后面全错，所以值得一个测试钉住。

class ApiClient {
  ApiClient(this._dio);

  final Dio _dio;

  factory ApiClient.create() {
    final dio = Dio(
      BaseOptions(
        baseUrl: currentEnv.apiBaseUrl,
        connectTimeout: const Duration(seconds: 10),
        receiveTimeout: const Duration(seconds: 20),
        // ★ 证书校验绝对不能关。见 6.3 的"两条合规红线"。
        validateStatus: (code) => code != null && code < 500,
      ),
    );
    return ApiClient(dio);
  }

  Future<T> get<T>(
    String path, {
    Map<String, dynamic>? query,
    required T Function(Object? data) fromJson,
    CancelToken? cancelToken,
  }) async {
    try {
      final res = await _dio.get<Object?>(
        path,
        queryParameters: query,
        cancelToken: cancelToken,
      );
      return fromJson(res.data);
    } on DioException catch (e) {
      throw e.toFailure(); // 归一化，禁止把 DioException 抛出这一层
    }
  }
}

/// DioException → Failure 的唯一映射表。
/// 放在这里而不是散落在各处，是因为"404 应该显示什么"必须是全局一致的。
extension DioExceptionX on DioException {
  Failure toFailure() {
    final code = response?.statusCode;
    if (code == 401 || code == 403) return const UnauthorizedFailure();
    if (code == 404) return const NotFoundFailure();

    return switch (type) {
      DioExceptionType.connectionTimeout ||
      DioExceptionType.sendTimeout ||
      DioExceptionType.receiveTimeout =>
        const TimeoutFailure(),
      DioExceptionType.connectionError => const NetworkFailure(),
      DioExceptionType.badResponse => ServerFailure(
          '服务异常（$code）',
          statusCode: code,
        ),
      DioExceptionType.cancel => const UnknownFailure('请求已取消'),
      DioExceptionType.badCertificate => const NetworkFailure('证书校验失败'),
      DioExceptionType.unknown => const NetworkFailure(),
    };
  }
}

class AuthInterceptor extends Interceptor {
  AuthInterceptor(this._ref);

  final Ref _ref;

  /// ★ 关键：所有并发请求共享同一个刷新 Future。
  /// 第一个请求发起刷新，后面的直接 await 它，不会重复刷。
  Future<String>? _refreshing;

  Future<String> _refreshToken() {
    return _refreshing ??= _doRefresh().whenComplete(() {
      _refreshing = null; // 刷完清锁
    });
  }

  Future<String> _doRefresh() async {
    // ...真正去调刷新接口
    return 'new-token';
  }

abstract final class AppRoutes {
  static const String home = '/';
  static const String cart = '/cart';
  static const String profile = '/profile';
  static const String login = '/login';
  static const String productDetail = '/product/:id';

  /// 详情页路径由函数生成，调用方不需要知道格式。
  static String productDetailPath(int id) => '/product/$id';

  /// 登录页带上"从哪来"，登录成功后能回原页面。
  static String loginPath(String redirectTo) =>
      '/login?from=${Uri.encodeComponent(redirectTo)}';

  /// 需要登录才能访问的路径前缀。
  static const List<String> protectedPrefixes = ['/cart', '/profile'];
}

final appRouterProvider = Provider<GoRouter>((ref) {
  /// refreshListenable 只需要一个"会通知我重新求值"的对象。
  /// 用一个自增计数器最稳：不依赖任何具体状态类型，
  /// 也不需要在 redirect 里自己比较前后值。
  final refresh = ValueNotifier<int>(0);
  ref.listen(authControllerProvider, (_, __) => refresh.value++);
  ref.onDispose(refresh.dispose);

  return GoRouter(
    initialLocation: AppRoutes.home,
    refreshListenable: refresh,
    errorBuilder: (context, state) => const NotFoundPage(),

    redirect: (context, state) {
      final loggedIn = ref.read(authControllerProvider).value ?? false;
      final loc = state.matchedLocation;

      final needsAuth =
          AppRoutes.protectedPrefixes.any((p) => loc.startsWith(p));
      if (needsAuth && !loggedIn) return AppRoutes.loginPath(loc);

      // 已登录就别再停在登录页
      if (loc == AppRoutes.login && loggedIn) return AppRoutes.home;

      return null; // null = 放行
    },

    routes: [
      // 带底部导航的三个 Tab：用 indexedStack 保住各自的滚动位置与页面栈
      StatefulShellRoute.indexedStack(
        builder: (context, state, navigationShell) =>
            MainScaffold(navigationShell: navigationShell),
        branches: [
          StatefulShellBranch(routes: [
            GoRoute(
              path: AppRoutes.home,
              builder: (context, state) => const ProductListPage(),
            ),
          ]),
          StatefulShellBranch(routes: [
            GoRoute(
              path: AppRoutes.cart,
              builder: (context, state) => const CartPage(),
            ),
          ]),
          StatefulShellBranch(routes: [
            GoRoute(
              path: AppRoutes.profile,
              builder: (context, state) => const ProfilePage(),
            ),
          ]),
        ],
      ),

      // 不在 Tab 里的页面：放在 shell 外面，自然就没有底部栏
      GoRoute(
        path: AppRoutes.productDetail,
        builder: (context, state) {
          // 参数是字符串，一定要自己校验 —— 路径对不代表参数对
          final id = int.tryParse(state.pathParameters['id'] ?? '');
          if (id == null) return const NotFoundPage();
          return ProductDetailPage(productId: id);
        },
      ),
      GoRoute(
        path: AppRoutes.login,
        builder: (context, state) => LoginPage(
          redirectTo: state.uri.queryParameters['from'],
        ),
      ),
    ],
  );
});

签名的三条底线① keystore 文件丢了你无法再更新这个 App——请同时备份到密码管理器；② 密码不要写进任何被提交的文件；③ CI 里用 repository secrets，用 base64 传文件：

# 本地把 keystore 变成一行文本，贴进 GitHub Secrets
base64 -w 0 upload-keystore.jks

附录 G · 升级检查单

这份文档里出现的所有"坑"——freezed 要 abstract、riverpod_annotation 会锁版本、import_lint 要求 Dart ≥ 3.10——都是版本变了之后才成立的。所以半年后你升 Flutter，会遇到"文档里没写的新坑"。这份清单就是那时候用的：按顺序跑，一次只改一类东西。

顺序命令看什么 / 为什么是这个顺序
① 备份git checkout -b chore/flutter-upgrade一定在分支上做。升级失败时你要能一键回到能跑的状态，而不是逐个撤销
② 升 SDKflutter upgrade
flutter doctor -v		先确认工具链本身干净。带着红叉升依赖，报错会互相掩盖
③ 看依赖flutter pub outdated先只读不写。看"Resolvable"列：能升的和被锁住的，一次看清
④ 升依赖flutter pub upgrade --major-versions跨大版本升级。升完先别改代码，让下面几步告诉你哪里断了
⑤ 看 lintflutter analyze规则集本身也升级了——very_good_analysis 新版会加新规则，可能凭空冒出几百条告警。分两批处理：先修真问题，再把"我认为不该守"的规则显式关掉并写注释说明原因
⑥ 跑测试flutter test测试是升级唯一的安全网。绿了才继续
⑦ 生成器dart run build_runner build --delete-conflicting-outputs生成器的产物格式会变，必须重跑。忘了这步会得到一堆看不懂的编译错误
⑧ 真机验证flutter run ×3 个环境dev / staging / prod 各跑一次。升级最容易破坏的是构建配置（Gradle、Podfile），而不是业务代码
两条纪律 ① 一次只升一类东西。同时升 Flutter SDK + 所有大版本依赖，出问题你无法定位是哪一边造成的——回退也没法回退一半。
② 别在发版前一周升级。升级引入的问题通常不是"编译不过"（那反而好办），而是"编译过了但运行时行为变了"。留出至少两周的观察期。

一个架构不会烂（lint 机器拦）、换数据源不动页面（依赖倒置）、改主题只改一个种子色（令牌）、加语言只加一个文件（i18n 工作流）、PR 不合规提不进主干（CI 门禁）的工程骨架。之后所有功能都是往这个骨架里填肉，而不是边写边改地基。
