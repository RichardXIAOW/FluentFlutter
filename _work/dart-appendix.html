附录 E · Dart 高级语法速查

前面 13 个阶段里出现过不少"看起来像关键字、但不知道它是干啥的"写法——sealed、final、copyWith、abstract final class……。这一节把它们一次讲清。每条都是它是干啥的 / 什么时候用 / 最常见的坑三段式，代码都能单独跑（贴进 dartpad.dev 或项目里的 _scratch.dart 即可）。

为什么这些语言特性跟"工程化"有关 它们不是炫技。每一个都在替你做一件机器能做的检查：sealed 让编译器替你找漏掉的分支；final 让编译器拦住手滑的二次赋值；copyWith 让状态更新变成"造一个新对象"而不是"到处改字段"。你少写一行检查，就少一个能在凌晨三点炸的 bug。

E.1 var / final / const / late final：我到底该用哪个

这三个是新手最容易糊在一起的。判断顺序只有一个，从上往下问：

lib/scratch/qualifiers.dartdart
// ── const：编译期常量。同一份字面量在整个 App 里只存在一份。
const double kPagePadding = 16;          // 字面量 → 可以 const
const Color kBrandSeed = Color(0xFF6750A4); // 构造函数是 const → 可以 const

// ── final：运行期只赋值一次。它是"实例字段"，每个实例一份。
class DemoController {
  final DemoRepository _repo;            // 构造进来后就不换了 —— 这正是我们要的
  const DemoController(this._repo);      // 构造函数能标 const 的条件：所有字段都是 final 且初始化表达式是常量
}

// ── final 局部变量：写代码时习惯性写 final，编译器帮你挡住手滑
void expand(List<String> raw) {
  final cleaned = raw.where((s) => s.trim().isNotEmpty).toList();
  // cleaned = [];                       // ← 编译错误，正合我意
  print(cleaned.length);
}

// ── late final：声明时不赋值，第一次读的时候才求值，且只求一次。
//    用于"依赖运行时上下文、但逻辑上只该算一次"的东西。
class CartPage {
  late final CartController controller = CartController();  // 用到才创建，不会被白创建

  // 也可以显式初始化（配合依赖注入）：
  // late final Analytics _analytics = Analytics(getIt());
}

什么时候真的用 late：只有两种正当理由——① 字段初始化表达式里需要 this（比如要调到别的方法）；② 昂贵对象想推迟到真正被读时才建。除此之外，late 是给"我保证赋值了"这句话打白条：如果你其实忘了赋值，运行时会在第一次读它的时候抛 LateInitializationError——比 null 更迟、更难查。

三个最常见的坑 ① const 不等于"值不变"，是"编译期已知"。const now = DateTime.now() 编译不过，因为 DateTime.now() 不是常量构造。
② final 只锁"引用"不锁"内容"。final list = []; 之后 list.add(1) 完全合法——final 保证的是这个变量名不再指向别的列表。想连内容都锁死，用 const [1, 2, 3] 或 List.unmodifiable(...)。
③ 公开 API 上别用 var 当字段。类的字段默认是 var（可变），等于把内部状态敞开给所有人改。约束应当是"默认 final，确实需要才放开"。

E.2 abstract / abstract final class / sealed：三种"我不能随便被继承"

这三个修饰符都在回答同一个问题：谁能继承我？答案不同，编译器能帮你做的检查也不同。

写法谁能继承 / 实现编译器能帮你检查什么典型用途
class X任何人，任何地方无普通业务类
abstract class X任何人；自己不能 new无（子类可能来自第三方）仓储接口、可扩展的基类
final class X同库内可继承；库外只能 new库外不许 extends不想让别人改我行为的类
abstract final class X没人能继承；自己也不能 new彻底封死，只能当命名空间用设计令牌容器（AppSpacing）
sealed class X同库内的子类，且全集已知switch 穷尽性检查（最强）失败类型、状态类型、UI 状态机

先说 abstract final class：纯常量容器

你在阶段 4 写的令牌类就是这个。它存在的唯一意思是"这个类只是给常量分组的命名空间，别 new 它、别继承它"：

lib/core/theme/app_tokens.dart（只摘 3 个值示意）dart
/// 间距令牌。abstract final class 是 Dart 的"static 命名空间"惯用写法。
/// - abstract：不许 new（构造一个只有常量的对象毫无意义）
/// - final   ：不许 extends / implements（否则别人可以改语义）
abstract final class AppSpacing {
  static const double xs  = 4;
  static const double sm  = 8;
  static const double md  = 12;   // 页面默认内边距
  // 完整清单（lg / xl / xxl）见阶段 4.1，以那份为准。
  // ⚠️ 别在这里"顺手补全"——同一份常量在文档里存两份，就一定会漂移。
}

// 用的时候：padding: const EdgeInsets.all(AppSpacing.md)
// 好处：全 App 只有这一处数字。设计说"内边距改成 20"，你改一行，不搜索替换。

// 反例 —— 别这样写，它会坑你：
// class AppSpacing { static const md = 12; }   // 能 new、能 extends，语义没人守
为什么是 abstract final 而不是 enum 或顶层常量 顶层常量（const kMd = 12;）会污染全局命名空间，且无法用类型系统分组——你没法写"接受一个间距令牌"的参数。枚举只能装整数等有限类型，装不下 double、Duration、Color。而 abstract final class + static const 两者兼得：有命名空间、有类型、零运行时开销（const 会被内联）。

再重点说 sealed：让编译器替你找漏掉的分支

sealed 的含义是：这个类的所有子类我都写在同一个文件里了，别人不可能再偷偷加一个。既然全集已知，编译器就能在 switch 时检查你有没有覆盖每一个分支——漏一个，直接编译报错，而不是运行时崩。

lib/core/error/failure.dartdart
/// 所有失败类型。sealed 保证：这个文件之外不可能存在别的 Failure 子类。
sealed class Failure implements Exception {
  const Failure(this.message);
  final String message;
}

/// 网络不可用 / 超时
class NetworkFailure extends Failure {
  const NetworkFailure([super.message = '网络不可用，请检查连接']);
}

/// 服务端返回了业务错误
class ServerFailure extends Failure {
  const ServerFailure(super.message, {required this.statusCode});
  final int statusCode;
}

/// 解析失败 / 数据格式不对
class ParseFailure extends Failure {
  const ParseFailure([super.message = '数据格式异常']);
}

/// 没登录 / Token 过期
class UnauthorizedFailure extends Failure {
  const UnauthorizedFailure([super.message = '登录已过期，请重新登录']);
}

现在用它的地方，穷尽性检查开始工作：

lib/core/error/failure_message.dartdart
/// 按失败类型给出用户可读文案 —— 注意：没有 default 分支，也不许有。
String messageOf(Failure f) => switch (f) {
      NetworkFailure()      => '网络好像断了，检查一下 Wi-Fi 或流量',
      ServerFailure(:final statusCode) => '服务器开小差了（$statusCode）',
      ParseFailure()        => '数据有点问题，我们已经在查了',
      UnauthorizedFailure() => '登录过期了，请重新登录',
    };

// ── 关键点来了 ──
// 半年后产品说"要加一个会员到期失败"。你在 failure.dart 里加：
//   class MembershipExpiredFailure extends Failure { ... }
// 然后你就没法编译通过了 —— messageOf 会报：
//   "The type 'MembershipExpiredFailure' is not exhaustively matched
//    by the switch expression."
// 编译器直接把"你忘了处理新情况"这件事拍在你脸上。
//
// ⚠️ 如果你手贱加一个 default / 通配 _ 分支，上面这份保护全部失效。
//    sealed + default 等于白用。
最常见的两种用错 ① 给 sealed 的 switch 加了 default: 或 _ =>。这是最可惜的——你付了 sealed 的代价，却把唯一的好处扔掉了。
② 把 sealed 的子类写到别的文件。编译不过，报 "The class 'X' can't be extended outside of its library because it's a sealed class."。子类必须和 sealed 父类在同一个文件（或用 part 拼进同一库）。
实践建议：把 sealed 层次放在一个 xxx.dart 里，几十行，天然内聚。如果你发现这个文件涨到 300 行，说明它其实是两个概念，该拆成两组 sealed。
什么时候该用 sealed（判断口诀） 当你写下这个类型的瞬间，脑子里能一口气数完所有可能情况——那就是 sealed。失败类型（网络/服务端/解析/未登录）、加载状态（初始/加载中/成功/失败）、订单状态（待付/已付/已发/完成/取消）、导航事件（跳转/返回/替换）。
反过来，如果你期望未来由第三方或别的团队来扩展（比如插件体系的基类），那就不能用 sealed——那应该用 abstract。

E.3 模式匹配：switch 表达式、when 守卫、:final 解构

sealed 是"类型全集"，模式匹配是"消费这个全集"的工具。它把原来一大坨 if (x is A) { ... } else if (x is B) ... 变成一段能穷尽检查的表达式。

lib/scratch/patterns.dartdart
// ── 1. 类型模式 + 顺手解构出字段（:final 就是"Dart，把这个字段绑成个局部变量"）
String describe(Failure f) => switch (f) {
      ServerFailure(:final statusCode, :final message)
          when statusCode >= 500 => '服务端崩了：$message',
      ServerFailure(:final statusCode)                       => '请求被拒（$statusCode）',
      NetworkFailure(:final message)                         => '网络问题：$message',
      _                                                      => '其他：${f.message}',
    };

// ── 2. when 守卫：同一类型下再按条件分岔。它必须紧跟在模式后面。
String trafficLight(int seconds) => switch (seconds) {
      final s when s < 0  => '非法',
      final s when s < 30 => '红灯',
      final s when s < 60 => '绿灯',
      _                   => '黄灯',
    };

// ── 3. record 解构：一次返回多个值，接收处直接拆开
({String name, int age}) parseUser(String raw) {
  final parts = raw.split(':');
  return (name: parts[0], age: int.parse(parts[1]));
}

void demo() {
  final (:name, :age) = parseUser('tom:18');   // 直接拆成两个局部变量
  print('$name is $age');

  // 列表 / Map 也能解构
  final [first, second, ...rest] = [1, 2, 3, 4, 5];   // first=1, second=2, rest=[3,4,5]
  final {'id': id, 'title': title} = {'id': 7, 'title': '耳机'};
  print('$first $id $title');
}

// ── 4. switch 语句（不是表达式）也能用模式，且可以没有 default —— 只要类型穷尽
void handle(Object event) {
  switch (event) {
    case int n when n > 0:
      print('正数 $n');
    case int():
      print('非正数');
    case String s:
      print('字符串 $s');
    default:
      print('其他');
  }
}
三条容易忘的语法规则 ① switch 表达式用 => 不用 case、不用 break，且必须返回值（或抛异常）。写成语句块时要用 => { ... yield x; }。
② when 必须紧跟在模式之后，且在 case/=> 之前。case int n when n > 0: ✅；case when n > 0 int n: ❌。
③ :final x 是 x: final x 的简写——只写 :final statusCode，Dart 自动把字段名 statusCode 绑成同名局部变量，省一次命名。:final code 想改名的完整写法是 statusCode: final code。

E.4 copyWith：谁生成的、为什么必须有它

copyWith 不是 Dart 关键字，它是一个约定俗成的方法名，由 freezed 或 json_serializable 这类代码生成器写进 .g.dart / .freezed.dart 里。你在 product_dto.dart 里能调它，是因为 build_runner 已经替你生成了。

它解决的问题：final 字段没法改。你要写的是状态管理，而状态管理要求"数据不可变"。既然不可变，改一个字段就只能造一个新对象——copyWith 就是这个"造新对象、其余字段照抄"的快捷方式：

lib/features/demo/data/demo_dto.dartdart
import 'package:freezed_annotation/freezed_annotation.dart';

part 'demo_dto.freezed.dart';   // ← freezed 会把 copyWith 生成到这里
part 'demo_dto.g.dart';         // ← json_serializable 把 fromJson/toJson 生成到这里

@freezed
abstract class DemoDto with _$DemoDto {   // ⚠️ freezed 3.x 强制要 abstract（或 sealed）
  const factory DemoDto({
    required String id,
    required String title,
    @Default(0) int likes,               // @Default 让字段可省，且 fromJson 缺字段时不炸
    @Default(false) bool favorited,
  }) = _DemoDto;

  factory DemoDto.fromJson(Map<String, dynamic> json) => _$DemoDtoFromJson(json);
}

// build_runner 生成的 _$DemoDto 里，等价于手写：
//
// DemoDto copyWith({
//   String? id,          // 注意：每个参数都是可空的 —— 没传 = 保持不变
//   String? title,
//   int? likes,
//   bool? favorited,
// }) => DemoDto(
//       id: id ?? this.id,
//       title: title ?? this.title,
//       likes: likes ?? this.likes,
//       favorited: favorited ?? this.favorited,
//     );

用起来的样子——状态更新就是"造一个新列表"：

lib/features/demo/presentation/demo_list_controller.dartdart
class DemoListController extends AsyncNotifier<List<DemoDto>> {
  @override
  Future<List<DemoDto>> build() => ref.watch(demoRepositoryProvider).fetchAll();

  /// 点赞：不原地改列表里的对象，而是生成一份全新的列表。
  /// 为什么非要这么绕？因为 Flutter 判断"要不要重建 UI"靠的是 == 。
  /// 原地改的话，新状态和旧状态 == 相等，界面根本不会刷新。
  void toggleLike(String id) {
    final current = state.value ?? const [];
    state = AsyncData([
      for (final item in current)
        item.id == id
            ? item.copyWith(likes: item.likes + 1, favorited: !item.favorited)
            : item,
    ]);
  }
}
copyWith 和 == / hashCode 是一套的 freezed 除了生成 copyWith，还会生成 ==、hashCode、toString，并且是按字段值比较，不是一个字段一个字段手写。
这两件事必须成对出现：没有值相等的 ==，不可变状态就是灾难——你每次 copyWith 都产生一个新对象，Flutter 一律认为"变了"，整棵子树白重建；测试里也没法 expect(result, expected)，只能去比每个字段。
所以你自己写 DTO 别手写类，用 freezed，或者至少让 IDE 生成 ==/hashCode。手写漏字段是高频事故。
三个高频坑 ① copyWith(x: null) 不会把字段设成 null。看生成的代码：x ?? this.x——传 null 等于"没传"。要把可空字段置空，freezed 会额外生成 copyWith 的替代方案（旧版用哨兵值 Object? x = freezed），现代 freezed 的推荐做法是声明成可空字段 + 用 copyWith(x: null) 之外的显式构造，或者干脆让这个字段不可空。
② 改了类但忘了重跑生成器。报"copyWith isn't defined"或参数对不上时，先跑 dart run build_runner build --delete-conflicting-outputs，别急着改代码。--delete-conflicting-outputs 不是可选项。
③ freezed 版本升级（2.x → 3.x）后，用 factory 构造的类必须加 abstract 或 sealed。否则报 "Missing concrete implementations of getter '_$DemoDto.id'"。这条在阶段 7.5 和附录 B 都提过，它就是这个报错的根源。

E.5 其他你会在真实项目里天天碰到的写法

extension：给别人的类加方法

lib/core/ext/context_ext.dartdart
/// 给 BuildContext 加几个快捷方式 —— 不用改 Flutter 源码，也不用包一层工具类。
extension BuildContextX on BuildContext {
  ThemeData get theme => Theme.of(this);
  ColorScheme get colors => Theme.of(this).colorScheme;
  TextTheme  get text   => Theme.of(this).textTheme;

  /// 一句弹 SnackBar，省掉 ScaffoldMessenger.of(context) 那一长串
  void toast(String msg) => ScaffoldMessenger.of(this)
    ..hideCurrentSnackBar()
    ..showSnackBar(SnackBar(content: Text(msg)));
}

// 用起来：context.colors.primary、context.toast('已收藏')
// 注意：调用点在 import 了 context_ext.dart 的地方才生效。

坑：① extension 不能被动态派发——编译期按变量的静态类型选方法，所以 Object x = ...; x.toast() 是调不到的。② 别用 extension 去覆盖已有方法名，容易造成"同一行代码在两个文件里行为不同"的诡异问题。用途应当是"加便利方法"，不是"改语义"。

mixin：横向复用行为，而不是靠继承

lib/core/paging/paged_mixin.dartdart
/// 分页逻辑的复用。多个 Notifier 都要"加载下一页"，
/// 用继承会逼它们共用同一个父类（不灵活），用 mixin 只借用行为。
mixin PagedMixin<T> on AsyncNotifier<List<T>> {
  int _page = 1;
  bool hasMore = true;

  @protected
  Future<List<T>> fetchPage(int page);

  Future<void> loadMore() async {
    if (!hasMore || state.isLoading) return;
    final next = await AsyncValue.guard(() => fetchPage(++_page));
    next.whenData((items) {
      if (items.isEmpty) hasMore = false;
      state = AsyncData([...state.value ?? const [], ...items]);
    });
  }
}

// 使用：注意 on AsyncNotifier<List<T>> 这个约束 ——
// mixin 只能贴到 AsyncNotifier<List<T>> 及其子类上，
// 编译器会检查，贴错地方直接报错。
class FeedController extends AsyncNotifier<List<Post>> with PagedMixin<Post> {
  @override
  Future<List<Post>> build() => ref.watch(feedRepoProvider).first();

  @override
  Future<List<Post>> fetchPage(int page) =>
      ref.read(feedRepoProvider).page(page);
}

mixin ... on X 里的 on 是访问权限声明：它告诉编译器"用我的类必须是 X 的子类"，于是 mixin 内部才敢直接调 state、ref 这些 X 提供的成员。别写裸 mixin M {} 再用 on Object 式的松散约束——那就退化成复制粘贴了。

async* / Stream：一次返回多个值

lib/scratch/streams.dartdart
/// async   → Future<T>   ：未来某一个值
/// async*  → Stream<T>   ：未来一串值（用 yield 往外推）
Stream<int> countdown(int from) async* {
  for (var i = from; i > 0; i--) {
    await Future.delayed(const Duration(seconds: 1));
    yield i;                       // ← 每 yield 一次，订阅方就收到一次
  }
}

// 消费：
// await for (final n in countdown(3)) { print(n); }
//
// 在 Riverpod 里对应 StreamProvider / StreamNotifier：
// final tickProvider = StreamProvider<int>((ref) => countdown(3));
// 在 widget 里 ref.watch(tickProvider) 会拿到 AsyncValue<int>，
// 每次 yield 都会重新触发一次 AsyncData。

什么时候用：实时性、多次推送——WebSocket 消息、倒计时、搜索结果随输入变化（debounce 后转成 Stream）、摄像头帧。什么时候别用：一次性请求就用 Future，硬套 Stream 只会让 ref.watch 的状态机更难读。

required 与命名参数：把"忘记传"变成编译错误

lib/scratch/params.dartdart
class DemoCard extends StatelessWidget {
  const DemoCard({
    super.key,                       // ← 永远带着它，否则 widget 无法正确复用
    required this.title,             // ← required：调用方不写就编译不过
    required this.onTap,
    this.subtitle,                   // ← 可空 = 可以不传
    this.trailing,                   // ← Widget? 同上
  }) ;

  final String title;
  final String? subtitle;
  final VoidCallback onTap;
  final Widget? trailing;

  @override
  Widget build(BuildContext context) => const SizedBox.shrink();
}

// 调用方必须写 title 和 onTap，其余可选：
// DemoCard(title: '耳机', onTap: () {});
一个可以当团队规矩的经验 对外暴露的 API，参数默认用 required；只有确实有合理默认值 / 语义上可为空时才放开。"这个字段忘了传"是最常见的 bug 之一，而 required 能让它在编译期就死掉——零成本，收益极高。反过来，如果某个参数你发现所有调用点都传同一个值，那它就该有默认值。

?.、??、??=、...：四个天天用的糖

lib/scratch/sugar.dartdart
String? name;

name?.length;              // 空安全调用：null 直接短路返回 null，不抛异常
name ?? '匿名';            // 空并：左边 null 就用右边
name ??= '默认名';         // 空并赋值：左边是 null 才赋值（不是 null 就什么都不做）
name!.length;              // 断言非空：你打包票它不是 null。为 null 会抛 —— 慎用

final a = [1, 2];
final b = [0, ...a, 3];    // 展开：[0, 1, 2, 3]
final m = {'x': 1, ...{'y': 2}};   // Map 同样支持

// ⚠️ name! 是"我比你（编译器）懂"。用它可以，但要确保你写过
//    if (name == null) return; 之类的守卫，否则就是把编译期错误
//    换成了运行期崩溃 —— 这是纯粹的倒退。

E.6 一页纸总结

写这个它的意思是你在本手册哪里见过
sealed子类全集已定，switch 必须穷尽；漏分支编译报错failure.dart、加载状态
abstract不能直接 new，可被任何地方继承仓储接口
abstract final class不能 new 也不能继承，纯命名空间AppSpacing 等令牌
final变量/字段只赋值一次（内容仍可变）几乎所有字段
const编译期常量，零运行时开销令牌、默认值
late final首次读取时才求值，只求一次延迟创建的 controller
copyWith由 freezed 生成：造一个改了部分字段的新对象状态更新
== / hashCode由 freezed 生成：按字段值比较，UI 才能判断"变没变"配合 copyWith
extension给已有类型加便利方法，不改原类context.colors
mixin ... on X横向复用行为，且限定只能贴到 X 的子类PagedMixin
async* / yield返回 Stream，一次推多个值实时数据、WebSocket
required命名参数必须传，否则编译不过Widget 构造、DTO
?? / ?. / ??=空值处理三件套，短路、兜底、条件赋值到处都有
怎么"真的学会"这些 不用背。你只要做一件事：下次写代码时，凡是你打出 if (x is A) 或 default:，先停下来想一秒——"这个类型是不是 sealed？我是不是漏了分支？"。坚持两周，这些就不再需要查表了。
